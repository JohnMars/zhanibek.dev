Thinking in coroutines, not threads

22 apr 2026 android 9 min read

After a decade of background-threading patterns on Android, switching mental models took longer than the syntax. Here's what finally clicked.

I wrote my first AsyncTask in 2015. By the time it was deprecated, I had a folder of opinions about how to do background work on Android - opinions about HandlerThread, about RxJava schedulers, about WorkManager versus a service. Coroutines arrived in 2019, but it took me almost two years to actually trust them. The syntax is the easy part. The mental model is the work.

The model isn't "lighter threads"

The first explanation everybody gets is that coroutines are "lightweight threads." This is technically true and pedagogically terrible. If you keep thinking in threads, you keep writing the same code, just with launch instead of Thread(). You miss the whole point.

The shift, for me, was: structured concurrency is a tree, not a pool. Every coroutine has a parent. When the parent dies, all children die with it. There is no orphan, no leak, no "I forgot to cancel that subscription." If you write a screen and tie its scope to viewModelScope, the world rights itself when the user backs out.

class FeedViewModel : ViewModel() {
  val state = MutableStateFlow(Loading)

  // scope dies with the ViewModel - children cancel automatically
  init {
    viewModelScope.launch {
      state.value = runCatching { repo.feed() }
        .fold(::Loaded, ::Failed)
    }
  }
}

Suspend, don't block

The second realisation: a suspend function is a contract about not blocking, not about which thread to run on. The dispatcher is a separate, orthogonal decision. Once I stopped sprinkling withContext(IO) around library code, my call sites got a lot easier to read.

If your suspend function chooses its own dispatcher, the caller can't compose. Make the choice once, at the edge - in the ViewModel, the worker, the test.

The Flow operators that actually pay rent

I used to teach a long list of operators. I now teach four:

  • map - for transformations.
  • combine - for joining two state streams into derived UI state.
  • stateIn - for upgrading a cold flow into something a screen can render.
  • onEach - for the analytics call you're definitely going to need.

Anything beyond those, I look up. Honestly. The mental cost of remembering forty operators isn't worth the tiny clarity gain over reading the docs once a quarter.

What I still get wrong

Cancellation. I get cancellation wrong all the time. The rule is simple - ensureActive() in tight loops, prefer cooperative APIs, never catch CancellationException - but the rule is simple in the same way "don't fall over" is simple. You'll fall over. Write a test that exercises cancellation; it's the only honest defence.

The thing I want to leave you with is that the work of switching mental models doesn't end when you can write a Flow. It ends when the model becomes quieter than the old one - when it stops generating decisions and starts absorbing them. Threads forced me to make a decision per side-effect. Coroutines let me make one decision per screen. That's a real change.
